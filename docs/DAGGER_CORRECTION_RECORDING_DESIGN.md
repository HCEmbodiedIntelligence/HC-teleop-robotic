## 当前配置、文件与下载

操作入口为 Dashboard 概览“人工干预与纠正采集”；先开启、等预备就绪，再开始程序。每次 Grip 使用已准备的片段槽，松手只关闭接收边界，写入、编码、导出和封存继续在后台执行。窗口之外只保留有界内存观测缓存，不持久化自主轨迹。

沿用 `ros.recording`，无需新增运行服务。`workflow: hc` 配 `format: mcap|lerobot|both`；现有仓库配置为 `both`，选择 LeRobot 时须先运行 `tools/setup_lerobot.sh`，或用 `LEROBOT_PYTHON` 指向已安装 LeRobot 0.4.3 的独立 Python。`workflow: platform_raw` 沿用 `capture_config_file`，其动作输入由 HC 最终输出证据提供。`derive_action_from_next_state` 必须为 false。

`ros.recording.corrections` 可省略，默认值如下；没有为此改写现有运行配置：

```yaml
corrections:
  prepared_slots: 4
  action_queue_items: 4096
  total_queue_bytes: 268435456
  observation_cache_bytes: 67108864
  observation_max_age_sec: 0.25
  late_message_sec: 0.2
  long_gap_sec: 0.2
```

`max_pending_jobs` 和 `min_free_bytes` 继续限制后台积压与磁盘空间。准备失败会显示原因，不能以“录制已就绪”开始程序。连续接管耗尽已准备资源时保留明确录制错误，不让编码/上传阻塞正常松手交还。

| --- | --- |
| MCAP 与质量/边界旁文件 | `runtime/topic_recordings/<recording_id>_correction.mcap` 和同名 `.correction.json` |

## 1. 数据应该怎样定义

建议采用 LeRobot DAgger 的 **corrections-only：只记录人工纠正窗口**。程序运行由人观察；需要介入时，人通过遥操作提供动作，这段动作连同机器人状态、相机观测一起保存。这里没有自动识别模型错误的算法。

| 概念 | 本方案的含义 |
| --- | --- |
| 人工干预 `intervention` | 当前样本的动作来自人工且通过 HC 最终输出检查 |
| 纠正片段 `intervention_id` | 一次有效接管到人工权限撤销之间的数据，有独立身份 |
| episode | LeRobot 中的一段连续序列；正常情况下，一次人工纠正导出一个 episode，不要求完成整个任务 |
| 异常原因 | 可选事后说明，如抓取偏移、姿态错误；系统不能仅凭握住 Grip 判定具体原因 |
| 任务成功 `outcome` | 独立于干预标记，缺省 `unknown`；松手不代表成功 |
| 采样质量 `quality` | 实际采样率、缺帧比例、连续缺口、源时间与边界覆盖；允许按规则容忍缺帧，不因缺号直接否定整段 |
| 文件完成状态 | 已收到的数据是否写完、文件结构和校验是否有效；与采样质量、平台质检分别判断 |

所以，这里收集的是“人如何从有问题的状态进行恢复或纠正”，不是把程序错误动作当作专家动作，也不是把所有人工操作自动标成成功示范。恢复到合适姿态本身也可以属于纠正数据。

选择只保存纠正数据，是结合用户偏好与 LeRobot 默认行为作出的设计建议。以后需要分析出错前的过程时可以另加上下文采集；本次不启用程序轨迹回溯，也不保存恢复程序后的延长片段。

## 2. LeRobot 实际怎样实现

核对版本：本机 `/home/hc_op/workspace/huqiong/hc_lerobot`，提交 `ede2267b24b628d6e2f475f9290131415f90d684`。在线 main 文档于 2026-10-19 交叉核对；在线版本会变化，具体代码行为以下列本地源码为准。

| 源码 | 核对到的行为 |
| --- | --- |
| [DAggerStrategyConfig](../../../../huqiong/hc_lerobot/src/lerobot/rollout/configs.py) | `record_autonomous=False` 为默认值，每个纠正窗口独立成 episode；开启后才记录自主与人工两类帧 |
| [rollout/context.py](../../../../huqiong/hc_lerobot/src/lerobot/rollout/context.py) | 运行策略循环前创建/恢复数据集；新建 DAgger 数据集增加布尔特征 `intervention`，shape 为 `(1,)` |
| [dagger.py 的 _run_corrections_only](../../../../huqiong/hc_lerobot/src/lerobot/rollout/strategies/dagger.py) | 进入 CORRECTING 后采集 observation、teleop action、task，调用 `dataset.add_frame()`，`intervention=True`；结束纠正时 `save_episode()` |
| 同上，AUTONOMOUS / PAUSED 分支 | corrections-only 模式下不向数据集添加程序运行或暂停帧 |
| 同上，`correction_tick` / `correction_stride` | 每段纠正从自己的录制计数起点开始，首个纠正 tick 参与录制，再按数据集频率采样；不会沿用程序阶段的采样余数而跳过首帧 |
| 同上，`_run_continuous` | 另一种模式记录两类动作并区分 intervention；它不是本次选择的采集方式 |
| [HighlightStrategy](../../../../huqiong/hc_lerobot/src/lerobot/rollout/strategies/highlight.py) | 用环形缓冲保留触发前的一段自主运行，再按用户输入保存；这是独立策略，不是 DAgger 默认暗中回录的数据 |

官方说明也明确区分默认的 corrections-only 与连续录制：[Policy Deployment / DAgger](https://huggingface.co/docs/lerobot/main/inference)。[HIL 数据采集说明](https://huggingface.co/docs/lerobot/main/hil_data_collection)介绍恢复与纠正过程，但其概念性操作流程不能代替某个具体策略的分段实现。

有三个细节不能照搬后误解：

1. 本地 DAgger 保存的人工 `action` 来自 `processed_teleop`；发给硬件前还经过 `robot_action_processor`。这不是电机实测执行结果。HC 需要明确自己的动作阶段，并保存最终输出来源证据。
2. 本地纠正循环的 `save_episode()` 在循环内执行，代码明确处理其阻塞时间；流式编码可以改善写入，但不能据此宣称没有延迟。HC 的正常松手恢复不等待这个操作。
3. `intervention=True` 本身不包含纠正成功或失败。LeRobot 另有 [HIL processor](../../../../huqiong/hc_lerobot/src/lerobot/processor/hil_processor.py)处理 RL 的 success/reward/termination；不能把那套奖励定义当作 DAgger 自动提供的标签，也不需要为了本功能接入 RL。

## 4. 面向操作者的流程

1. 会话开始时选择任务/现有录制配置，启用“人工干预与纠正采集”。系统准备资源，显示“准备中”，准备完成显示“纠正采集就绪”。这一步只做一次。
2. 程序通过原有 ServoJ 运行。此时不保存程序运行的图像、状态和动作轨迹到纠正产物。
3. 握住 Grip：HC 撤销程序权限；准备人工控制时绑定本次纠正片段；人工目标生效后自动录制，不需要按 X 或点击录制。
4. 松开 Grip：HC 关闭人工权限和本段接收范围；后台保存该段，同时执行交还事务，程序恢复。没有额外确认或保存按钮。
5. 再次握持：新的片段立即使用已经准备好的资源；上一段可以还在后台编码。

界面分别显示“谁在控制”和“是否正在采集”：例如“程序控制 / 纠正采集就绪”“人工控制 / 正在采集第 12 段”“程序控制 / 第 12 段保存中”。后台完成才显示已保存；采样质量、导出、上传和平台质检各自显示。允许出现“已保存 / 少量缺帧 / 等待网络”的组合，不把少量缺帧显示成文件保存失败。

## 5. 为什么不会等握住后才启动录制

### 5.1 预备阶段：提前完成耗时工作

在允许此次采集会话进入 AUTO 之前，完成：

- 检查目录、磁盘空间、配置、关节名称/单位、所需相机与反馈源，并冻结配置快照。
- 启动并保持采集进程、ROS 订阅和写入服务；等待需要的相机及状态源实际收到新鲜数据，不能只检查进程存在。
- 准备消息类型、序列化与媒体处理资源；完成至少一轮不发布机器人命令的采集通路预热，结果不作为正式数据。
- 分配有界缓冲、片段描述槽和待写文件资源。至少准备当前可用槽与下一槽，池容量按设备流量和积压上限配置，不能无限分配内存。
- 确认“预备槽可接收数据、写入端可用、必需源新鲜”，生成可消费的就绪凭据。后续持续监测，资源失效时撤销就绪状态。

预备期间只维护有限的最新观测用于健康检查和首帧对齐，不持久化整个自主过程。不加载模型、不调用推理暂停接口、不创建第二条机器人控制链。

### 5.2 接管时：只绑定片段与打开接收范围

接管开始先撤销程序控制，不被录制操作拖延。在人工控制准备完成、开放第一条人工命令之前：

1. 消费预先准备的片段槽，绑定 `session_id / intervention_id / controller_instance_id / control_epoch`。
2. 在控制权限的有序边界记录 `manual_open`，同步设置采集端可见的片段描述。实现可采用版本化共享状态与有界事件队列；不能只依靠迟到的 ROS 状态话题或网页回调。
3. 开放人工输出。最终输出边界给每条成功发出的人工目标附上该片段的递增 `command_seq`，向独立采集通路提交相同身份的动作证据。
4. 采集端把观测、动作、媒体关联到这个片段，写入工作由后台处理。

不能只存一份“当前片段编号”：极短接管可能在采集线程下一次调度前已经结束。开始/结束记录必须进入预先分配的有序边界日志，直到采集端确认处理并写完待保存数据才回收；相机按这份历史边界归段，动作携带自己的片段身份。即使采集端稍后处理，也能识别完整的短片段。日志和媒体缓冲都有容量与溢出统计，不能用覆盖旧边界的方式维持表面正常。

这条路径不得包含进程启动、DDS 首次发现、依赖导入、相机打开、目录扫描、视频编码、文件关闭、fsync 或无界队列等待。片段身份使用预分配资源绑定；持久化作业日志由后台接收有序事件完成。

正常条件下，采集范围必须在第一条人工命令之前建立。若预备资源突然不可用，仍必须先撤销程序；按第 9 节报告采集故障，不能假装开始成功、过几秒再补一个“完整”的片段。

### 5.3 松手时：关闭范围，后台写完待保存数据

在同一有序控制边界撤销人工权限并记录 `manual_close`，冻结 `last_command_seq` 与截止时间。后续新命令不能再带着这个片段的有效发布资格。

这里原来使用的“排空”（drain）指**把队列中待保存的数据逐条写完**，不删除录制文件，也不把队列里尚未保存的数据直接丢掉。具体过程为：

1. 冻结本段截止边界，接收端停止把范围之外的新数据加入本段；各来源报告本段最后接收的记录位置。
2. 后台写入器继续读取队列，把动作/状态写入 MCAP，把本段图像交给编码器；截止点前采集但迟到的相机包按约定期限归入本段。
3. 处理到各来源已确认的末尾后，让编码器输出其内部尚未写出的帧，完成视频尾部、MCAP 索引及文件关闭；按持久化策略刷新文件并记录结果。
4. 文件完成后释放相应的内存缓冲与片段槽，生成作业结果和质量统计。磁盘上的原始录制与导出产物继续保留，供下载、上传或重试。

控制交还与这些后台步骤并行。例如松手时还有三帧已接收图像待写，它们会继续写入；不会为了让队列看起来为空而删除它们。内存条目写入后被释放，与删除磁盘上的录制数据是两回事。

实施前 [TopicRecorder.stop()](../middleware/core/topic_recorder.py) 会在满队列时丢弃数据以塞入 `None`。现已改为独立完成标志，等待所有已接受事件写入后关闭；已用暂停写进程、填满队列、调用停止、恢复写进程的测试确认不因正常停止丢数据。

恢复后的程序动作使用不同来源和代际，即使它们先到达采集进程也不会进入旧片段。相机包需要依据采集时间而非仅依据到达时间归属：截止点之后曝光的帧不加入；不能确定时间归属的包标记无效，不猜测。

等待迟到数据有配置的期限，不能永远等一个已经断流的相机。到期后保存已经收到的内容，并记录超时源和实际覆盖。短缺口按第 6.4 节评估，不直接把整段判废；写入失败、文件无法正常结束或控制来源无法确定，需要单独标为失败/待核查。序号只用于定位覆盖差异，不能重建没有收到的数据。

### 5.4 一个完整时间例子

以下是解释机制的示例时间，不是性能测量结果。

| 时间 | 控制侧 | 采集侧 |
| --- | --- | --- |
| 会话开始 | 尚未开始此次程序控制 | 启动订阅/写入服务，准备缓冲与片段槽；全部就绪后允许 AUTO |
| 12.000 s | 收到 Grip 按下，立即撤销程序 | 取得预备片段槽；没有临时启动录制进程 |
| 12.040 s | 清理和重锚定完成，开放人工控制 | 打开片段 C12；第一条人工目标编号 1，连同首帧观测进入 C12 |
| 12.040–12.240 s | 人工操作 | 持续收集本段状态、图像和人工目标 |
| 12.240 s | 收到正常释放，撤销人工，准备交还 | 关闭 C12，冻结末动作序号 20；内存里还有 3 帧图像待写 |
| 12.270 s | 程序新命令通过校验后执行 | 新程序动作不进入 C12；后台继续处理此前的 3 帧图像 |
| 12.300 s | 再次接管（若发生） | 从另一预备槽开启 C13，不等待 C12 编码完成 |
| 稍后 | 不受 C12 封存影响 | 检查 C12 的序号、媒体和时序；已写完就标已保存，采样质量另行展示 |

这个例子中的 40 ms 接管准备时间不属于人工纠正动作。系统分别报告控制交接耗时与录制增加的耗时，不用前者掩盖后者。

## 6. 首尾帧、时间与采样质量

### 6.1 首帧

人工控制获得权限时记录边界，但“握住 Grip”事件本身不作为一条动作。首条真实人工目标到达最终输出边界后，建立第一条动作证据；短暂按下后在接管完成前松开，只产生一次取消事件，不生成伪造的人工 episode。

首帧关联已经准备好的最新有效相机/状态观测，检查源时间和最大年龄。类似 LeRobot 的“先观察、再动作”，初始图像的曝光可以略早于首条人工动作；它是这条纠正样本的输入观测，不是额外保存一段自主轨迹。只保留组成首帧所必需的有限观测，不把预备缓存整段倒进数据集。相机标定等静态元数据可随片段复制。

每段独立从首个可用纠正样本开始数据集采样，不沿用上一段采样计数。所需相机/状态缺失时不能用黑图或零状态冒充有效首帧；保留已收到的人工动作证据，报告边界覆盖不足。

### 6.2 末帧和乱序到达

片段控制区间按 `[manual_open, manual_close)` 定义。动作归属同时要求来源为人工、实例/代际/片段匹配，且序号未越过冻结的结束边界；不能只用时间比较，也不能看到当前 UI 是 MANUAL 就把动作标成人工。

相机和反馈保留源时间、接收时间与时钟质量。迟到但实际属于区间内的消息在限定收尾时间内接收；源时间越过截止点的消息不因排队延迟而进入旧段。初始观测按第 6.1 节单独记录其边界角色。时钟跳变、同步失效和不确定的跨边界曝光必须显式标记，不能延长窗口来吞入程序动作。

两次接管有各自的缓冲与身份。C12 的迟到包不能因为 C13 已开始就写成 C13；上一段末帧也不能沿用到下一段成为人工动作。

### 6.3 原始动作证据与训练采样分别检查

最终输出的每条人工命令均记录证据，不在这条证据流上做录制限频。它包含目标向量、公共名称/单位、来源、实例/代际、片段、命令序号和发送时间；沿用 `action_stage=sent` 并增加 `action_boundary=hc_final`，明确表示 HC 已向硬件适配器发出，不声称电机已经执行。实际状态另从反馈记录。控制回调只提交小型动作证据，不搬运图像或做媒体编码。

起止记录在控制侧冻结：`first_command_seq / last_command_seq / emitted_count`。采集侧计算唯一已收数量、差异区间与重复数量，对照控制侧计数和声明的采样策略。序号连续性作为诊断指标，**不作为“一缺号就判整段不可用”的条件**。还要看时间缺口、动作有效期、状态覆盖、相机覆盖与原因。结束边界丢失造成来源/归属不可判定时，才需要隔离相关范围核查。

相机优先使用源帧号和曝光时间检查缺帧。设备没有可靠源帧号时，只能根据接收统计、时间间隔和驱动状态评估覆盖，必须报告这一限制，不能把接收端自己连续编号当成相机从未掉帧的证明。

LeRobot 的 20/30 Hz 等频率属于导出采样，控制可能为 100 Hz。原始动作证据以尽量保留完整序列为目标，导出按固定策略重采样；导出帧引用的动作序号不连续是正常的。即使原始流偶尔丢一条消息，也应先评估其对该时间范围的影响。采样配置、时间戳和映射必须可追溯。

### 6.4 缺帧容忍与文件完成分开

| 情况 | 采样质量与使用方式 |
| --- | --- |
| 按配置降采样、相机与控制频率不同 | 正常记录采样映射，不算异常丢帧，也不要求序号相邻 |
| 偶发缺帧、短时间间隙仍在配置容差内 | 保存并允许下载/上传，记录提示和实际帧率；按该流允许的对齐策略使用，不整段判废 |
| 必需流出现较长缺口或某区间失效 | 原始段保留、可下载/上传供平台质检；标出受影响时间范围，训练时排除该范围或导出连续有效子段 |
| 整段缺少必要模态、严重错时或人工/程序来源不明 | 保存能保留的原始内容和诊断，标为待核查；不能伪装成正常训练样本 |
| 文件写入失败、缺少实际文件或校验不符 | 文件状态 failed/interrupted；这是文件完成问题，需要恢复或重试，区别于可读文件内少量采样缺帧 |

质量规则以当前 profile、源频率和任务要求为基础，记录最大片段内时间间隙、有效样本比例、首尾覆盖及允许年龄，不使用统一的“零缺号”门槛。具体容差应复用/扩展既有配置并用目标相机实测确认，不能在此承诺所有任务通用的丢帧百分比。

允许同一片段内、有效期内按既有语义取最近有效观测/目标；状态插值要遵循对应流的规则。超过有效期的值保留无效掩码，不能用下一帧状态伪造人工命令或跨控制边界填补。训练读取器若不会处理掩码，导出时切成可用的连续子段并保留共同 `intervention_id` 与原时间位置；不能删除中间缺口后把两边直接拼成连续动作。

**文件已保存、数据适合某种训练、平台质检通过是三个状态。** 少量缺帧不阻止本地保存/下载或正常上传，也不改变 Grip 接管/释放的控制行为。

## 7. 保存内容与导出

| 内容 | 保存方式与语义 |
| --- | --- |
| `observation.state` | 真实机器人反馈，按 profile 公共关节名和 SI 单位组织 |
| `observation.images.*` | 配置选定的实际相机，保留帧身份、源时间/接收时间和有效性 |
| `action` | 通过 HC 最终输出检查的人工关节/夹爪目标，记录明确动作阶段；不从下一帧状态生成 |
| `intervention` | LeRobot 布尔特征，shape `(1,)`；本数据集的有效动作帧为 true |
| 片段元数据 | session/recording/intervention 身份、实例和代际、任务、profile/配置快照、起止原因、首尾动作序号 |
| 时效和质量 | 源年龄、时间质量、缺失序号、队列丢弃、相机覆盖、正常结束或中断 |
| 评价 | `outcome=unknown/success/failure`、可选说明及来源；握持/释放不会自动生成成功标签 |

推理端持续发来的 ServoJ 在人工期间仍被拒绝，不作为此片段的 action，也不全量保存为另一路程序轨迹。可保留拒绝计数等少量控制诊断元数据，它不属于程序运行数据集。

采集模式独立于现有保存格式：复用所选的 MCAP 或 platform_raw 工作流，并在源写入前应用纠正片段范围。raw 的原始包、RGB 视频与深度保存入口都要受同一范围约束；只在导出时过滤不够。每段视频需能独立解码，不能依赖上一段或自主阶段的预测帧。

LeRobot 导出新增纠正专用处理：

1. 通常一个已完成的人工片段对应一个 episode；连续松手再握持产生两个 episode，不能跨中间的 AUTO 拼接。
2. 对齐只使用本段来源证据和有限首帧观测；沿用明确的源时间/有效期，动作不做跨权限边界插值。记录 `active_at_sample` 或实际选择的时序定义，不能把“当时有效的已发目标”说成反馈状态或另一次模型输出。
3. 保留原始证据和时间跨度。按第 6.4 节容忍短缺口，较长缺口只影响对应范围；普通导出器的无效占位不能直接当作有效专家样本。不因少量缺帧隔离整段，不删除中间缺帧后压缩时间。
4. 不按时长自动丢掉短纠正。哪怕只有少量有效样本也保留并标注短段；没有任何有效训练样本时保留控制/动作诊断记录并报告原因，不计为成功 episode。
5. 增加 bool 特征后，用实际 HC 写入环境与官方 LeRobotDataset 验证帧数、dtype、episode 边界、视频首末帧及动作维度。禁止训练 action chunk 跨 episode；必要的尾部 padding 使用读取器规定的 mask。
6. 导出是训练数据准备，不自动启动训练或混入旧训练集。纠正产物接入普通采集相同的 UploadService，按会话选择及既有绑定/自动入队配置上传；断网先本地留存，详见第 10 节。

## 8. 采集状态与后台生命周期

会话采集状态与每段保存状态分开，避免“上一段保存中”占住下一段的采集入口。

| 会话状态 | 含义 |
| --- | --- |
| `PREPARING` | 初始化/预热，不显示可用，不启动此次纠正采集 AUTO |
| `ARMED` | 资源、源与预备槽就绪；等待接管，不持续落盘自主轨迹 |
| `CAPTURING` | 当前人工片段正在接收 |
| `DEGRADED` | 源或持续写入能力不满足约定，显示具体原因；偶发、容差内缺帧只记质量提示 |
| `STOPPED` | 会话结束，待保存片段独立收尾 |

每段仍复用 RecordingService 的 `capturing → draining → source_complete → exporting → ready` 等作业阶段与失败/中断状态，其中 draining 在界面显示为“写入收尾中”。ready 表示文件产物已完成，采样质量另列；正常结束但带少量缺帧提示的文件可以 ready。未写完或崩溃的文件不能标 ready。创建新段不能返回上一段的 active 路径；需要改造现有服务的准备与分段边界，而不只是重复调用 `start()`。

普通 X/Y 手动录制与自动纠正采集共用资源管理。首版建议两者在同一录制服务上互斥：开启纠正模式时已有普通录制则报告占用；纠正会话中 X/Y 不新建或截断纠正段，并提示当前采用 Grip 自动分段。普通模式仍保留原操作。已有人工标记可关联当前纠正段用于事后复核，不增加必须按的键。

## 9. 资源不足和故障

录制有界缓冲按实际相机/深度/动作数据率计算字节预算与可承受积压时间，不能只设置一个消息条数。后台预备下一片段、写完上一片段与编码分开调度；慢视频编码不能阻塞段切换或占住所有采集资源。

| 情况 | 处理 |
| --- | --- |
| 会话开始时订阅/相机/写入服务尚未就绪 | 保持 PREPARING 并显示阻塞项，不允许以“录制就绪”开始此次 AUTO；普通控制模式不受影响 |
| 接管发生时录制槽意外耗尽或写入故障 | 先撤销程序，人工介入能力不等待磁盘恢复；明确显示未完整录制/录制失败，记录缺口，不能静默晚启动并称为完整段 |
| 人工期间偶发缺帧或短暂队列溢出 | 按实际缺口、比例和源语义记录质量提示，继续保存；不直接判废整段，不触发控制 HOLD |
| 严重源缺口或写入故障 | 明确显示受影响范围/写入错误并保留可恢复内容，停止声称采集正常；纯录制故障不阻塞人工控制或正常松手交还。若机器人控制本身也丢失必要反馈，按独立的控制故障规则处理 |
| 正常释放 | 冻结边界并后台写完待保存数据；控制交还不等编码/导出 |
| VR 断连、跟踪失效、控制故障、急停 | 立即关闭对应控制/片段边界，记录真实结束原因；不把它伪装成正常松手或任务成功 |
| 极短按压、尚无人工动作 | 仅保留控制事件；不保存空的成功 episode |
| 松手后立刻再握持 | 新身份、新预备槽；上一段继续写入收尾，包不能串段 |
| 进程崩溃或断电 | 作业记 interrupted；已写数据可按现有机制恢复为新产物，不能保证尚在内存的数据已落盘 |
| 磁盘接近阈值或长期吞吐不足 | 提前撤销“可持续采集”就绪状态并显示积压；不可无限扩大缓冲或后台无提示丢数据 |
| 平台断网或上传慢 | 本地采集/写入/下载继续，上传队列等待并按规则重试；不当作采集或机器人控制故障 |

正常路径重点保证启动及时、结束不主动丢弃待写数据、缺口可定位，并按配置允许正常采样波动和少量缺帧。采样损失、写入失败和网络不可用分别报告；任何录制或上传阻塞都不能阻止人工撤销程序控制。

## 10. 数据平台、离线保存与下载

### 10.1 与普通数据采集共用上传链路

**本次方案包含与普通采集相同的平台上传能力。** 纠正片段继续使用 RecordingService 作业、现有格式、完成产物和 UploadService；不做一套需要人工从隐藏目录搬运的孤立文件。

已核对的现有能力与新增范围：

| 内容 | 现有事实 / 本次补齐 |
| --- | --- |
| 保存后上传 | RecordingService 先完成本地源文件，再发布 ready 描述；UploadService 只接收已完成的产物 |
| 平台格式 | 现有上传器支持 `hc_mcap`、`hc_lerobot`、`platform_raw`，分别走 MCAP、LeRobot v3、CAPTURE_BUNDLE；纠正采集沿用这些格式 |
| 断网恢复 | Queue 使用本地 SQLite 保存任务与上传身份；Worker 对可重试网络错误退避重试，并核对服务端已完成分片 |
| 上传后留存 | 当前上传 worker 没有上传成功后删除源录制的步骤；本方案继续默认保留本地源文件和已生成导出 |
| 普通网页下载 | 当前 app.py 已有 MCAP 直接下载和 LeRobot 目录 ZIP 下载 |
| raw 下载 | 当前 resolve_dataset 不支持 raw 目录；本次新增按 recording_id/产物身份下载源包和封存包的入口，包含未绑定平台但已写完的本地 raw 源包 |
| 平台识别纠正属性 | 保留 `intervention`、片段身份和质量报告，并验证平台接入、处理、再次导出不会丢失；这项端到端验证尚未完成 |

平台接口及归属规则参照 [机器人身份直传 Raw](../../../../hc_DataPlatform/docs/robot-authenticated-ingest.md)。协议已经支持分片恢复和不可变上传身份；“上传完成”“平台处理完成”“质检通过”分别显示，不能互相代替。平台尚未适配的机型处理能力也不能仅因文件上传成功就宣称已经支持。

### 10.2 正常操作与断网操作

会话开始时沿用普通采集的平台机器人与采集任务绑定，选择已有的自动上传设置；无需每次握住/松开 Grip 重新填写任务。流程为：

```text
人工纠正片段
  → 写完本地原始数据并记录质量
  → 按配置完成 LeRobot 导出或 raw 封存
  → 发布各自的完成产物
  → 进入本地持久上传队列
  → 有网络时分片上传/提交
  → 平台处理与质检
```

本地原始数据的保存不依赖后续导出或平台成功。MCAP 已写完而 LeRobot 导出失败时，仍可下载原始 MCAP并单独重试导出。

- 已有平台绑定、网络断开：正常录制并本地保存；已配置自动入队的产物进入等待重试，网络恢复且服务运行时继续处理。普通缺帧提示不阻止上传。
- 首次离线、尚无平台绑定：先保存本地源数据和元信息，状态为“待绑定/未上传”；恢复连接后选择任务再封存/入队，不影响本地下载。
- 已入队后切换页面上的任务：旧段仍归原来的冻结绑定，不随新默认任务漂移。
- 凭据无效、平台任务停用或服务器会话终止：单独显示需处理原因，不能把所有失败都当作普通断网无限创建新上传。

少量缺帧的数据可以像普通数据一样入库，由平台继续质检。字节数、SHA-256、实际文件清单不匹配属于文件或传输错误，仍按现有规则拒绝；这与视频采样中偶发缺帧是不同问题。

当前仓库 [middleware/config.yaml](../middleware/config.yaml) 配置为 `uploads.enabled=false`、`auto_enqueue=false`。会话沿用已配置绑定并显示上传状态；本次未修改这两个设置或启动生产上传。

### 10.3 纠正标签如何随数据进入平台

每段记录任务、机器人/profile、`session_id / intervention_id`、采集起止时间、来源、结束原因和采样质量。LeRobot 数据内保留布尔 `intervention`；MCAP 用录制元数据/事件保存同样的来源和片段信息；raw 包通过已支持的元数据资产携带，纳入清单与校验。

上传源格式与 `capture_mode` 沿用既有合法值，不新增一个平台无法识别的“DAgger 格式”。需要透传的摘要使用协议允许的 `format_metadata` 或已有资产；现有 ready 描述采用严格字段校验，不能随意追加顶层字段。确需扩展契约时同时更新生产端、上传适配器与平台消费/测试，并保持旧普通录制兼容。

复用 `source_artifact_id` 关联原始录制与 LeRobot 导出；平台不能把两个格式当作两次不同的人为纠正来重复统计。每次 Grip 片段的控制身份与平台任务绑定保持可追溯。平台对 `intervention` 的归一化展示/筛选及再次导出需专项验收，不仅检查上传接口返回成功。

### 10.4 本地文件具体放在哪里

文件首先保存在机器人本机，网络失败不会使它只存在于上传缓存。复用当前录制目录，不额外创建只有纠正功能知道的存放位置。

按本仓库 `middleware/config.yaml` 的默认相对路径解析，录制根目录 R 为：

```text
/home/hc_op/workspace/teleop_ws/src/HC-teleop-robotic/runtime/topic_recordings/
```

| 内容 | 路径规则 |
| --- | --- |
| MCAP 原始录制 | `R/<recording_id>_<文件名>.mcap` |
| LeRobot 导出目录 | `R/lerobot/<源文件名去掉扩展名>/`，含 meta、data、videos 等 |
| raw 封存上传包 | `R/sealed/<artifact_id>/` |
| raw 采集源目录 | 实际 capture 配置的 `storage.directory/<native_session_id>/`；相对路径按 capture 配置文件所在目录解析，不假定一定在 R 内 |
| 录制作业记录 | 默认 `HC-teleop-robotic/runtime/recording_jobs/` |
| 上传队列及重试状态 | 默认 `HC-teleop-robotic/runtime/upload_queue/queue.sqlite3`；这里存队列，不是图像/视频正文 |

这些是配置解析结果；本次检查的工作区中默认 runtime 目录尚不存在，不能据此推断当前部署的历史数据位置。运行时若使用另一份配置，应以 `GET /api/recordings` 的 `directory`、`GET /api/recording/jobs` 中该作业的 `path` 及 raw 配置快照为准。拟在每段详情显示“本地位置”和各产物路径，提供复制路径，避免用户手工推算。

默认保留本地原始数据及已生成导出，上传成功不自动删除，退出会话也不删除。磁盘不足时提示并拒绝无法保存的新采集，不静默清除历史纠正片段。这里的本地留存是本机上的一份副本；本次没有承诺额外磁盘或异机备份。用户可通过下载、外接盘复制或平台上传形成另一份副本。

### 10.5 怎么下载

当前普通采集的网页操作：打开 HC Dashboard → “数据集管理” → 找到已经保存的记录 → “下载”。MCAP 下载原文件；LeRobot 下载包含数据、元数据和视频的 ZIP。当前配置默认端口为 7876：机器人本机可用 `http://localhost:7876`，其他电脑通过机器人局域网地址访问；这只是默认地址说明，本轮没有验证或启动网页服务。

现有接口为 `GET /api/recordings/{identifier}/download`，其中 LeRobot 的 identifier 形如 `lerobot:<目录名>`。此接口是机器人本地下载，不依赖数据平台或公网。下载完成后的临时 ZIP 清理只删除临时打包文件，不删除原始数据集目录。

纠正采集还需补齐统一作业下载：

- 在同一个列表按片段显示“原始数据 / LeRobot / raw 整包”的可用下载项；文件写完即可本地下载，不要求先上传或平台质检通过。
- 已实现 `GET /api/recording/jobs/{recording_id}/download?kind=source|lerobot|sealed`；服务端从作业身份与冻结路径解析目标，raw 未绑定时仍可下载已完成的 source。
- 单文件返回文件，多文件包在后台打成 ZIP 或流式归档。读写/删除锁、归档容量限制沿用现有基础；下载不得干扰下一段采集，不允许下载正在变化的半成品作为完成包。
- 若完全没有网络连接，可在机器人本机网页下载或将已完成文件/目录复制到 U 盘、移动硬盘；只断公网但局域网可用时，电脑仍可从 HC 网页下载。

## 11. 时效、质量和平台联动验收

先做无机器人输出的合成/回放源测试，再接隔离 fake rig，最后在目标机型、实际相机配置和实际存储介质上测量。下面是拟定验收目标，不是已经取得的结果。

| 指标 | 定义及拟定要求 |
| --- | --- |
| 预备准确性 | ARMED 前完成实际源数据检查、通路预热和下一段资源准备；不能先亮就绪再启动订阅 |
| 录制新增的接管开销 | 控制已具备开放人工条件到片段接收范围建立的额外耗时：目标 P99 ≤ 10 ms、观测最大 ≤ 20 ms；与 Motion 停止/重锚定时间分别测量 |
| 首条动作覆盖 | 验证片段接收已在第一条人工目标前建立；不得由临时启动造成开头整段漏录，偶发采样缺口按源时间与容差记录 |
| 末条动作覆盖 | 有明确结束边界与末条已接收记录；正常收尾不为插入停止标记丢弃队列数据，末端覆盖按时间容差评估 |
| 相机边界覆盖 | 第一/最后可用样本与人工区间边界差值满足配置的源周期、时间质量和允许延迟；不能仅靠动作完整推断相机完整 |
| 采样计数 | 每段独立计时，按实测源和声明 FPS 校验导出行数、时间跨度与原始帧映射，明确重采样而非静默漏帧 |
| 正常松手交还 | 不等待视频编码、导出、网络上传或上一段文件关闭 |
| 正常负载 | 在声明的相机/控制频率与存储配置内达到约定采样率、缺口容差和首尾覆盖；统计实际丢帧，不能把“不允许任何缺号”作为数据可用门槛 |
| 过载 | 统计损失并定位影响范围；严重持续不足显示 DEGRADED/写入错误，少量波动仅提示；控制抢占时间不被磁盘队列拉长 |
| 上传/下载 | 缺帧提示不阻止已完成文件下载或入队；断网可保存、服务重启后队列恢复，有网后续传，无重复片段归属 |

必须覆盖的具体场景：

1. 100–300 ms 的短接管，正常源条件下得到首末动作证据及相应观测；不能等松手才开始采集。
2. 短于一个相机周期的接管，验证首帧快照时效及实际可形成的样本数；不能要求不存在的新曝光或伪造末帧。
3. 连续至少 100 次短接管，后台同时编码多段，验证首尾、身份隔离、预备槽补充与资源回收。
4. 程序在人工期间持续高频发送变化较大的目标，检查纠正动作中没有程序来源。
5. 按可控方式延迟旧相机包、结束事件和动作证据，验证迟到消息正确归段、超时缺口可见。
6. 慢盘、队列满、相机断流、编码失败、作业重启，核对质量分级、文件完成、控制独立性和重试身份；尤其验证停止时不挤掉队列数据。
7. 时间戳倒退/时钟重置、快速释放重握、TAKEOVER 中松手、RETURNING 中重新接管，不能生成跨段动作或虚假 episode。
8. MCAP 与已启用的 raw 路径分别检查持久化内容，不能在视频、原始包或自动导出中残留未选择的自主运行段。
9. LeRobot 官方读取器验证首帧/末帧、episode 索引、bool intervention、公共关节向量、视频解码、有效性和 action chunk 边界。
10. 人为降采样、偶发缺一帧与较长连续缺口分别注入；前两者不能直接整段判废，后者定位到受影响范围，均保留原始记录供下载/平台质检。
11. 先断网再录制，以及上传一半断网/重启服务：本地数据保留，已配置绑定的队列持久化，同一上传身份恢复分片，无重复 Raw 或错绑任务。
12. 未绑定平台时录制，核对 source 已完成即可本地下载；后续绑定、封存/上传不需要重新录制。
13. MCAP、LeRobot、raw 源包及封存包下载逐一验证；下载内容与源清单/校验一致，临时归档清理不删除源数据。
14. 通过普通平台任务上传纠正片段，验证接入、处理/质检状态、原始下载及可用的再次导出保留 intervention 与片段/质量信息；不以“已上传”替代数据链路验收。

对外报告分别给出“接管反应时间”“录制范围打开时间”“数据进入有界队列时间”“写入/封存完成时间”。文件晚于松手完成不等于晚开始采集；判断依据是来源证据、帧时间、队列计数与最终覆盖，而不是保存提示出现的时刻。
